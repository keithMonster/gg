# Reflection: 组织归属之外的四条行为边界
### 给父会话的最终输出
**新增 orgId 最容易改变的并非界面，而是旧请求遇到故障、撤权和后台恢复时还能不能执行；这些行为才是“无感”的承重面。** 当前全体 iDesk 用户属于川锅，已由 Keith 本轮明确，不再保留“首批可能来自不同组织”的假设。归属川锅不改变 guest、员工、服务身份与禁用状态。

开题：把问题重写为“怎样给已运行系统增加第二条组织坐标，同时保持已有操作的身份、授权与结果连续”。错误判据是旧会话因新增依赖失能，或新组织继承旧主体的资源／凭据／全局阻断；分别看断联恢复、授权拒绝、实际执行目的地与执行次数。对比过一次大切换、仅补标签便宣称多组织两种方向，前者混合过多失败源，后者没有隔离证据；选择先保全旧闭环、再以双组织闭环证明隔离。本轮最便宜一击是固定 SHA 读源码，已直接核会话缓存、个人接线、调度与 unknown 阻断，未运行系统。

**1. 成员停用与旧会话离线可用的语义尚需先固定。** 问题：新稿“membership 独立检查、失联不把未知当有效”若落成每请求远查，会改变旧会话的故障行为。反例：川锅用户持有效持久会话，底座临时不可达；旧系统可继续打开会话，新 guard 却全部拒绝。反方向用缓存，又不能声称底座一停用就全平台立即拒绝。已核 `/Users/xuke/CGProject/cg-weilu` main `8f8255aa4da43389a7756f85956acc9a8b96e4cd` 的 `server/src/platform/verified-session.ts:79–109` 在内存／DB 命中时不问中心；`server/src/common/auth.guard.ts:476–484` 只在 miss 回源。需核证据：重启＋断底座的旧会话回放，以及停用动作到 iDesk 拒绝的完整回执。建议：底座拥有 membership 真源；iDesk 使用受控同步的本地持久资格投影，旧热会话不增加逐请求远程依赖；未映射、过期或不能证明有效的身份才拒绝／回源。首批只做受控停用流程，只有底座变更和 iDesk 本地拒绝状态均已确认才报告“已对 iDesk 生效”；部分失败显示待生效，不把底座写成功冒充完成，也不承诺尚未接入应用的实时撤销。停止新派发／新外呼，已发生的副作用仍允许对账收尾。**级别：阻止这部分 guard／管理契约直接定稿，不阻止取证与加法式基础开发；验证未过阻止身份真实切换。**

**2. “接线关联组织”不能只用群的 ownerOrgId 选凭据。** 问题：组织启用权、凭据所有者、实际执行端是不同关系。反例：哈轴成员在川锅群调用自己的企微工具，若按群组织取连接会使用别人的企业／个人凭据；同账号双组织标签页触发本地插件，仅凭 userid 回执又不能证明动作仍在发起时的组织上下文。已核同 SHA `server/src/weilu/wecom.connect.service.ts:104–129` 按 userid 复用个人连接；`server/src/weilu/local-plugin.service.ts:68–87` 定向该 userid 浏览器并检查同人回执。需核证据：每类接线的供给绑定来源、真人／确认者传递、浏览器 dispatch 与回执冻结上下文。建议：企业供给按获准资源组织绑定；个人连接按实际账号及连接自己的明确绑定选择；本机执行保持本人端点与发起上下文。组织 enable/grant 只赋予调用资格，不转移个人凭据；保留现有连接，不要求现有用户重连。**级别：阻止“一律按资源组织找连接”的 schema／resolver 落地；只阻止对应接线的多组织开放，不阻止其他路径开发。**

**3. 后台隔离要同时隔离执行身份与失败影响范围。** 问题：加入 orgId 后，定时任务仍可能借旧安装人执行，一个组织的 unknown 仍可能冻结其他组织。反例 A：安装人的 membership 停用后，组织日报静默停摆；为维持日报而自动换群主／服务账号，则无声换了授权主体。反例 B：川锅某 app 的外调结果 unknown，第二组织同 app 也收到 OPERATION_UNKNOWN。已核同 SHA `server/src/app-runtime/host.service.ts:303–306` 使用 installed_by 创建日程 action；`:253、257、328、433` 的 recordScope=app 以 business_domain='*' 跨同 appKey/env 阻断。`scheduled-jobs.ts:58–77` 还按全局首个安装及 appKey/day 去重。需核证据：同 app 两组织中一方 unknown／停用安装人／重启，另一方仍执行；旧 completed、running、uncertain occurrence 不被改键重放。建议：旧个人委托链保持真实主体并按其停用语义停止，不能自动升级成组织服务身份；确需组织自主任务再显式建其授权。orgId 纳入存储、scope、business_domain、去重、恢复与全部 unknown 查询闭包；旧川锅 operationId、dispatchId、occurrence 与外呼去重身份保留。**级别：阻止相应任务／runtime 契约含糊落地；只阻止相关双组织真实启用，组织基础可以继续。**

**4. S0＋S1 要交付一条闭合行为链，不能只交表和组织选择。** 问题：横向把 org 字段铺开，可能很晚才发现旧缓存身份没有新 accountId、guest 被员工化，或 Agent 实际执行越过组织目录。反例：新登录测试全绿，旧持久会话从不重新 resolve，首个读取旧私人助理的请求却找不到新映射而创建空空间。需核证据：旧员工 token、旧持久会话、guest、禁用身份各自从入口走到旧资源；新旧权限结果对照；两组织实际执行通道的越界测试。建议将施工分为下列可单独验收的里程碑，而不另建大型撤销／调度基础设施。**级别：不阻止开发；闭环未过阻止该路径切换，执行边界未过阻止第二组织真实数据进入。**

最小闭环顺序：**① 川锅归属闭环**——稳定 orgId 幂等初始化，按可信来源给现有 iDesk 身份建立显式映射，旧缓存命中后也能补齐 account／membership；保留全部旧 ID 和旧权限。先验“旧凭据→同一旧私人空间／群→一笔本地新写带川锅归属→重启恢复→断底座仍符合既有资格语义”；该链不需要同时改发 token、ASR、模型与所有接线。完成后仍只称川锅归属接续，未称多组织完成。**② 双组织应用／任务闭环**——同账号、同 appKey、每组织至少两个安装，验组织内共享保留、组织间读写与 unknown 阻断分开、每组织只执行一次、撤权和重启不重放；再各取企业供给、个人连接、本机执行的一条真实代码路径验证。**③ 第二组织启用门槛**——Agent 文件／程序权限的真实隔离小样与旧客户端／文件／全量已用应用保全并行推进；全部可达路径闭合后才开放第二组织真实数据，公共能力继续逐项切 cg-platform-services。旧热会话兼容与真实执行隔离都是具体验收，不靠第二组织 UI 藏起来代替。

未发现需要推翻共用底座、同库逻辑隔离或保留旧 ID 的依据。跨组织私聊产品语义、新登录渠道、全平台即时撤销可后置；不能拿它们阻挡已明确的川锅基础。程序执行隔离已在现稿识别，属于既有实施门槛，我没有以纸面审查宣布通过。已读 wiring-audit，但它使用较新的 main SHA；上述承重结论均补核父会话允许的旧固定 SHA。未核线上版本、真实数据、浏览器或运行隔离，也未运行应用、测试、网络或外部调用。
复核回执：主代理修订后，我重读了当前推进稿 §2–§6。上述四条已准确吸收：S1 限川锅归属与旧链路旁路对账，不加远程准入、不启新停用流程；membership 传播／断联／任务委托语义在 S2 实施前固定；接线明确三维；unknown 纳入组织隔离验收。接受把新增停用流程从 S1 推迟到 S2，这比我最初建议的首批受控停用范围更窄，仍保留既有禁用机制。当前不再把这些列为阻止 S1 开发的问题。只剩实施门槛：旧缓存身份映射及断联回放、个人接线冻结上下文、同 app 两组织多安装的 unknown／停用／重启测试、实际执行隔离。文案有一处宜澄清：§4“组织管理首批统一补齐”及“成员加入／停用”应明确 S1 仅受控初始化／维护，新增停用语义落 S2，避免跟后文分期冲突；这不阻挡取证与基础开发。
### 核心假设
Keith 本轮“现有所有用户都属于川锅”成立；这里只界定现有 iDesk 身份，不推定外围数据库人员均应导入。共享底座与首批川锅为目标边界；上述本地资格投影只是受控缓存，不成为第二套 membership 真源。
### 可能出错的地方
实际线上写方、旧票据类型及所有个人连接绑定字段未核；投影停用流程若没有可靠完成回执，建议会退化成“写了真源但应用仍放行”。不宣称概率。
### 本次哪里思考得不够
只读定向源码，没有实际执行环境与库快照；跨组织回执、Agent 执行限制和迁移时长无法由本轮验证。已避免用最新 wiring-audit 的行号冒充父会话固定旧 SHA。
### 如果 N 个月后证明决策错了，最可能的根因
首批“归属接续”的窄闭环被当作全部多组织已完成，遗漏后台旧写方，或把应用本地资格缓存误当独立管理真源。
